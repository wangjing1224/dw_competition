# 任务 15：规则分级与批量智能审核重构

## 1. 目标

重构当前“每个投标文件 × 每条规则启动一次主 Agent”的审核方式，解决规则数量失控、模型调用次数过多、上下文重复膨胀和资料核验循环过深的问题。

本任务完成后：

- 招标规则按固定业务分类抽取、归并，只设置最多 30 条的总量上限，不设置下限。
- 每条规则具有重要程度和默认核验深度。
- 每个投标文件在建立索引和进入主 Agent 前，先生成详细审核摘要并完成项目相关性路由。
- 明确不相关或无法确定相关性的文件停止建立投标索引和智能审核，但仍生成包含摘要、理由和人工复核信息的完整结果。
- 相关文件的全部规则一次性交给主 Agent，不再逐条规则启动 Agent。
- 主 Agent 能看到与规则分类一致的精简资料目录，只对确有资料且值得核验的声明调用子 Agent。
- 资料核验子 Agent 保留自主检索能力，但最多运行 3 轮，只负责核心资料核验。
- 主 Agent 允许根据全部规则审核需要执行多轮工具调用，轮数上限通过配置控制，不与子 Agent 共用 3 轮限制。
- 所有业务结构化模型结果统一使用 Prompt 注入 Schema、模型直接输出 JSON、代码执行 Pydantic 校验的 `prompt_only` 方式。
- JSON 是唯一事实来源，Word 忠实呈现 JSON，不再过滤不相关文件或其他已记录结果。

## 2. 当前问题

当前主审核流程按文件和规则双重循环：

```text
投标文件 1
  -> 项目适用性判断
  -> rule-1 Agent
  -> rule-2 Agent
  -> ...

投标文件 2
  -> 再执行全部规则
```

若 3 个投标文件对应 260 条规则，仅规则工作单元就达到：

```text
3 × 260 = 780
```

每个工作单元还可能包含投标响应检索、规则原文回查、资料核验子 Agent 和最终收口，实际模型调用次数远高于 780，无法满足比赛评分标准中的算力消耗和运行效率要求。

本任务不通过增加并发掩盖该问题，而是减少规则数量、工作单元数量和无效工具调用。

## 4. 总体流程

```text
招标文件
  -> 统一解析
  ├-> 章节切片 -> Embedding -> 招标依据索引
  └-> 章节大批次分类抽取
      -> 分类归并
      -> 策略校正
      -> 不超过 30 条最终规则

投标方资料
  -> 统一解析
  -> 一次 LLM 生成资料细分类和双用途视图
  -> 章节切片 -> Embedding -> 资料索引
  -> 生成与规则分类对应的精简资料目录

投标文件
  -> 统一解析
  -> 一次 LLM 完成详细数据清洗摘要并判断项目相关性
  ├-> not_matched：保留摘要和理由，不建索引、不进主 Agent
  ├-> uncertain：保留摘要和不确定理由，不建索引、不进主 Agent，转人工复核
  └-> matched：
      -> 章节切片 -> Embedding -> 投标文件索引
      -> 按规则分类预检索相关片段
      -> 主 Agent 一次审核全部规则
      -> 必要时回查规则原文
      -> 必要时调用资料核验子 Agent
      -> 主 Agent 收口
      -> 代码确定性汇总 JSON
      -> Word 忠实呈现 JSON
```

索引构建继续使用现有“章节/表格边界 + 章节内部 Token 切分”逻辑，不引入 Chat LLM。

## 5. 规则抽取、分类和分级

### 5.1 最终规则模型

规则固定使用六个业务分类：

```python
class RuleCategory(StrEnum):
    FORMAT = "format"                         # 形式与完整性
    QUALIFICATION = "qualification"           # 资格与合规
    COMMERCIAL = "commercial"                 # 商务响应
    TECHNICAL = "technical"                   # 技术响应
    PERFORMANCE_CAPACITY = "performance_capacity"  # 业绩与履约能力
    CONSISTENCY_RISK = "consistency_risk"     # 一致性与风险
```

项目名称、招标人、包号和物资类别等适用性信息进入项目摘要，不再作为普通审核规则循环执行。

规则增加两个独立维度：

```python
class RulePriority(StrEnum):
    CRITICAL = "critical"    # 否决、准入、核心参数等重点要求
    IMPORTANT = "important"  # 影响评审或履约的重要要求
    NORMAL = "normal"        # 一般完整性和规范性要求


class VerificationLevel(StrEnum):
    BID_ONLY = "bid_only"              # 只检查投标文件响应
    SOURCE_CHECK = "source_check"      # 需要回查招标原文
    EVIDENCE_CHECK = "evidence_check"  # 需要核验投标方资料
    CROSS_CHECK = "cross_check"        # 需要跨文件一致性核验


class RuleCheckItem(StrictModel):
    item_key: str
    requirement: str
    operator: str | None = None
    expected_value: Any | None = None


class RuleItem(StrictModel):
    rule_id: str
    category: RuleCategory
    priority: RulePriority
    verification_level: VerificationLevel
    name: str
    requirement: str
    check_items: list[RuleCheckItem]
    severity: Severity
    evidence_required: bool
    required_evidence_types: list[EvidenceType]
    source: SourceRef
```

一组同类技术参数应形成一条复合规则及多个 `check_items`，不得将每个表格单元拆成独立规则。

### 5.2 按章节大批次增量抽取

Embedding 片段只服务检索，规则抽取继续使用较大的章节批次。每个批次一次输出当前内容涉及的全部分类，没有内容的分类返回空数组。

```python
async def extract_rule_candidates(parsed_documents):
    accumulated_outline = empty_rule_outline()
    candidates = []

    for document in parsed_documents:
        for batch in build_rule_extraction_batches(document):
            response = await invoke_structured(
                model=rule_extraction_model,
                messages=[
                    build_rule_extraction_prompt(
                        source_context=batch,
                        categories=RULE_CATEGORIES,
                        existing_outline=accumulated_outline,
                    )
                ],
                output_type=CategorizedRuleExtractionBatch,
            )

            candidates.extend(attach_sources(response, batch))
            accumulated_outline = update_compact_outline(
                accumulated_outline,
                response,
            )

    return candidates
```

`existing_outline` 只保留已覆盖审核点名称，不把全部历史规则再次注入：

```json
{
  "technical": ["检测器分辨率", "测温范围", "通信接口"],
  "commercial": ["报价", "交货期", "质保期"]
}
```

### 5.3 分类归并和总量限制

全部批次完成后，按分类集中归并一次：

```python
FINAL_RULE_LIMIT = 30


async def finalize_rule_set(candidates):
    grouped = group_by_category(candidates)
    merged_rules = []

    for category, category_candidates in grouped.items():
        merged = merge_equivalent_requirements(category_candidates)
        compound = combine_related_items_as_compound_rules(merged)
        merged_rules.extend(compound)

    return enforce_total_limit(
        rank_by_priority_and_audit_value(merged_rules),
        limit=FINAL_RULE_LIMIT,
        preserve_priority=["critical", "important"],
    )
```

只设置总量硬上限，不设置分类上限、分类下限或各优先级数量配额：

- 最终规则可以少于 30 条，不为满足数量而补写规则。
- 某一分类可以规则较多，也可以为空，由招标文件实际内容决定。
- 超过 30 条时，优先保留 `critical`，其次保留 `important`，剩余空间保留 `normal`。
- 归并和复合规则用于减少重复、相近和过细规则，不为了平均分类数量而删除真实重点要求。

### 5.4 代码校正规则策略

LLM 在抽取时初步生成 `priority` 和 `verification_level`，普通代码负责校正明显不合理的组合：

```python
def normalize_rule_policy(rule):
    if rule.severity == "fatal":
        rule.priority = "critical"

    if rule.evidence_required:
        rule.verification_level = "evidence_check"

    if rule.category == "consistency_risk":
        rule.verification_level = "cross_check"

    if (
        rule.check_type in {"presence", "parameter_compare"}
        and not rule.evidence_required
    ):
        rule.verification_level = "bid_only"

    return rule
```

重要程度决定规则是否值得深入审核；核验深度决定默认使用投标文件、招标原文、投标方资料或跨文件信息。

## 6. 投标文件摘要与相关性路由

### 6.1 详细审核摘要和路由结果

摘要节点不仅负责路由，还承担投标文件进入主 Agent 前的数据清洗。它需要尽量完整地提取主 Agent 后续初审和检索规划所需的关键字段，但不直接判断具体规则是否合规。

```python
class BidDocumentSummary(StrictModel):
    file_id: str
    summary: str
    document_type: str
    project_name: str | None
    buyer: str | None
    bidder_name: str | None
    package_numbers: list[str]
    material_categories: list[str]
    product_names: list[str]
    model_numbers: list[str]
    category_overview: dict[RuleCategory, str]
    key_sections: list[str]
    match_status: Literal["matched", "not_matched", "uncertain"]
    match_reason: str
    confidence: float
```

其中：

- `summary` 是可直接提供给主 Agent 和最终报告的详细自然语言摘要。
- 结构字段用于减少主 Agent 再次从长文中提取项目、包号、物资、产品和型号等基础信息。
- `category_overview` 按规则分类概括当前文件已包含的响应内容，不代替正式规则审核。
- `match_status` 只负责判断该文件是否可以自动进入当前项目审核。

### 6.2 每个文件一次 LLM

```python
async def summarize_and_route_bid_document(
    parsed_document,
    project_profile,
    rule_category_outline,
):
    context = build_adaptive_document_context(
        parsed_document,
        max_context_tokens=48_000,
        include_file_name=True,
        include_section_titles=True,
        include_key_sections=True,
        include_tables=True,
    )

    return await invoke_structured(
        model=bid_chat_model,
        messages=[
            render_prompt(
                "bid_document_summary",
                project_profile=project_profile,
                rule_category_outline=rule_category_outline,
                document_context=context,
            )
        ],
        output_type=BidDocumentSummary,
    )
```

小文件优先传完整解析文本；超过上下文预算时，按章节标题、关键章节、表格和首尾内容构造自适应输入。摘要模型应尽量完整地清洗和归纳投标内容，但不执行具体规则合规判断。

### 6.3 路由位置

```python
async def prepare_bid_documents(documents):
    prepared = []

    for document in documents:
        parsed = parse_document(document)
        summary = await summarize_and_route_bid_document(parsed, ...)

        if (
            summary.match_status == "not_matched"
        ):
            prepared.append(
                build_not_applicable_result(
                    document=document,
                    summary=summary.summary,
                    reason=summary.match_reason,
                    confidence=summary.confidence,
                )
            )
            continue

        if summary.match_status == "uncertain":
            prepared.append(
                build_route_manual_review_result(
                    document=document,
                    summary=summary.summary,
                    reason=summary.match_reason,
                    confidence=summary.confidence,
                )
            )
            continue

        prepared.append(
            PreparedBidDocument(
                document=document,
                summary=summary,
                needs_index=True,
            )
        )

    await build_document_index(
        documents=[
            item.document
            for item in prepared
            if item.needs_index
        ]
    )
    return prepared
```

路由原则：

- `matched`：建立索引并进入主 Agent。
- `not_matched`：不建立投标索引、不进入主 Agent，保存明确排除理由。
- `uncertain`：不建立投标索引、不进入主 Agent，直接形成文件级人工复核结果。
- 如果模型给出低置信度或理由不足，程序应将结果规范化为 `uncertain`，不得交给只看到摘要的主 Agent再次猜测相关性。
- `not_matched` 和 `uncertain` 文件都不得删除，必须进入最终 JSON 和 Word。

这里的 `uncertain` 是文件路由层面的“大不确定”：摘要节点已经看过当前可用的完整投标内容，仍无法确认是否属于项目，继续自动审核没有可靠依据。

已确认 `matched` 的文件进入主 Agent 后，仍可能在具体规则、原文或资料核验中出现“小不确定”，这些问题按规则形成 `manual_review` Finding，不影响其他规则继续审核。

## 7. 与规则分类一致的资料目录

### 7.1 底层细分类保留

现有 `EvidenceType` 用于索引过滤，继续保留合同、发票、证书、营业执照、技术参数、检测报告、生产能力、人员和售后等细分类。

### 7.2 一次资料分类生成两种用途视图

资料分类模型只调用一次，但输出需要同时包含：

1. `catalog_profile`：面向主 Agent，说明该资料可服务哪些规则分类、可核验哪些主题。
2. `retrieval_profile`：面向资料子 Agent和检索工具，保存资料自身的标题、实体、关键词和可搜索事实。

```python
class EvidenceCatalogProfile(StrictModel):

    summary: str
    verifiable_topics: list[str]


class EvidenceRetrievalProfile(StrictModel):
    document_title: str
    entities: list[str]
    keywords: list[str]
    searchable_facts: list[str]


class EvidenceClassification(StrictModel):
    evidence_type: EvidenceType
    confidence: float
    classification_status: ClassificationStatus
    reason: str
    catalog_profile: EvidenceCatalogProfile
```

同一种底层资料可以服务多个业务分类，例如合同既可用于商务交易核验，也可用于业绩核验。

```python
class EvidenceCatalogEntry(StrictModel):

    count: int
    summary: str
    evidence_types: list[EvidenceType]


def build_evidence_catalog(classified_documents):
    return {
        category: EvidenceCatalogEntry(
            available=bool(matches),
            count=len(matches),
            summary=compact_catalog_profiles(matches),

        for category in AUDIT_CATEGORIES

```

目录聚合 `catalog_profile`，只提供规则类别、数量、简短说明和可核验主题，不把资料正文或完整文件清单放入主 Agent上下文。

资料索引保留 `retrieval_profile`。资料子 Agent检索时可结合 Claim 的关键词、核验点和资料自身的关键词、实体进行召回，不依赖主 Agent目录摘要完成细粒度检索。

## 8. 主 Agent与资料核验子 Agent

### 8.1 主 Agent前置检索

程序按规则分类构造检索查询，并提前准备少量高相关片段：

```python
async def build_grouped_retrieval_context(file, rule_set):
    context = {}

    for category, rules in group_rules(rule_set).items():
        query = build_category_query(category, rules)
        results = await retrieval.search(
            query=query,
            file_ids=[file.file_id],
            candidate_top_k=20,
            final_top_k=5,
        )
        context[category] = deduplicate_and_trim(
            results,
            max_chunks=5,
            max_chars_per_chunk=1_500,
        )

    return context
```

主 Agent可在摘要不足时继续调用受控工具，但不得对每条规则机械地重复检索。

### 8.2 主 Agent一次审核全部规则

主 Agent一次收到当前文件的：

- 项目摘要。
- 投标文件摘要。
- 不超过 30 条分类规则。
- 按分类组织的投标响应检索片段。
- 与规则分类一致的精简资料目录。
- 必要的任务身份信息。

```python
async def bid_agent_node(state):
    response = await bid_chat_model.bind_tools(

            retrieve_rule_source_tool,
```

主 Agent首轮需要：

1. 对全部规则形成初审结果。
2. 对投标文件中明确且足够的信息直接形成结论。
3. 只为重点或重要规则提出必要的原文回查。
4. 只为存在具体投标声明、要求资料证明且资料目录存在对应类别的规则提交 Claim。
5. 对资料目录中不存在的类别记录“缺少可核验资料”，不调用子 Agent。

主 Agent轮数上限通过配置控制，默认建议为 8，不与资料子 Agent共用固定的 3 轮限制：

```text
第 1 轮：审核全部规则并决定是否调用工具
第 2 轮：读取工具结果，必要时补充最后一次工具调用
后续轮次：按需读取规则原文、投标响应或资料核验结果
信息充分时：立即输出最终批量审核 Decision
```

```yaml
audit:
  bid_agent_max_steps: 8
  evidence_agent_max_steps: 3
```

主 Agent不要求运行满 8 轮；没有工具需求时可以首轮直接结束。达到配置上限仍未返回合法结果时，代码生成可追踪的 `manual_review`，不得无限循环。

子 Agent只负责当前 Claim 的资料核验：

```text

第 2 轮：并行回查最相关的 1～3 个候选原文
第 3 轮：返回简洁 EvidenceReviewResult
```

- 一句简洁摘要。

- 明确一致性问题。
- 必要的人工复核原因。


普通规则默认只做投标响应初审；发现异常时才允许升级审核深度。

## 9. AuditState与结果汇总

### 9.1 新主图

```text
Prepared Audit Context
  -> 读取下一个相关投标文件
  -> 构造分类检索上下文
  -> bid_agent
  -> 工具或资料子 Agent
  -> 批量审核 Decision
  -> apply_file_audit_output
  -> 下一相关文件
  -> 合并预路由的不相关文件结果
  -> build AuditResult
```

主状态不再使用 `current_rule_index`：

### 9.2 批量 Decision和确定性汇总

```python
class BatchAuditDecision(StrictModel):
    file_id: str
    findings: list[Finding]
    evidence_results: list[EvidenceReviewResult]
    summary: str


def apply_batch_audit_decision(state, decision):
    validated = BatchAuditDecision.model_validate(decision)
    expected_rule_ids = {
        rule.rule_id
        for rule in state.rule_set.rules
    }
    actual_rule_ids = {
        finding.rule_id
        for finding in validated.findings
    }

    # 所有规则必须有结果；复合规则的子检查项在 Finding 内保留。
    require_complete_rule_coverage(
        expected_rule_ids,
        actual_rule_ids,
    )
    validate_sources_and_ownership(validated, state)

    file_result = build_file_result_deterministically(
        document=state.current_bid,
        summary=state.current_bid.summary,
        findings=validated.findings,
        evidence_results=validated.evidence_results,
    )
    return advance_to_next_file(state, file_result)
```

最终结论继续由代码按确定性顺序计算，不由模型自由改写：

```text
non_compliant > risk > manual_review > compliant
```

### 9.3 路由和失败策略

- 主 Agent轮数上限由 `bid_agent_max_steps` 配置，默认建议为 8。
- 子 Agent最多 3 轮。
- 模型结构化输出失败只修复一次。
- 单次检索默认返回 3～5 个片段。
- 同一资料片段在同一文件审核中不重复回查。
- 超时或达到步数上限时转为人工复核。
- 文件级审核第一版默认顺序执行；算力平台验证稳定后再将文件并发提高到 2。

### 9.4 统一 Prompt-only JSON

所有业务结构化模型结果统一使用：

```yaml
structured_output_mode: prompt_only
```

适用范围：

- 规则抽取结果。
- 投标方资料分类结果。
- 投标文件详细摘要和路由结果。
- 主 Agent最终批量审核 Decision。
- 资料子 Agent最终核验结果。

实现约束：

```text
提示词注入目标 JSON Schema
  -> 普通 ChatModel 调用
  -> 模型只返回 JSON
  -> 本地 Pydantic 校验
  -> 失败时只执行一次格式修复
```

主 Agent和资料子 Agent中间仍使用 LangChain 标准 `tool_calls` 调用 `BaseTool`；`prompt_only` 约束的是最终业务结构化结果，不重新实现一套 JSON 工具调用协议。

## 10. JSON与Word一致输出

### 10.1 输出原则

```text
审核流程决定结果
  -> AuditResult 完整保存为 JSON
  -> Word 只读取已落盘 JSON
  -> JSON 中有什么，Word 就展示什么
```

Word 不再过滤 `not_applicable` 文件。所有上传的投标文件都必须出现在 Word 中：

- 相关文件：显示全部规则结果、资料核验和建议。
- 不相关文件：显示文件摘要、匹配状态、排除理由和置信度。
- 不确定文件：显示继续审核的原因和人工复核提示。

```python
def generate_word_report(json_path):
    audit_result = read_and_validate_json(json_path)
    document = create_report_document()

    for file_result in audit_result.file_results:
        render_file_overview(document, file_result)

        if not file_result.is_applicable:
            render_not_applicable_reason(
                document,
                summary=file_result.document_summary,
                reason=file_result.exclusion_reason,
                confidence=file_result.match_confidence,
            )
            continue

        render_findings(document, file_result.findings)
        render_evidence_results(document, file_result.evidence_results)

    return save_word(document)
```

保持当前“一份任务级 JSON、每个投标文件一份 Word”的输出组织，不额外改成任务级单 Word。每个 JSON `FileAuditResult` 都必须生成对应 Word，包括 `is_applicable=false` 的不相关文件，不允许静默过滤。

## 11. 模型和上下文约束

目标算力平台：

- Chat LLM：Qwen3.5 9B，64K上下文，OpenAI兼容接口。
- Embedding：vLLM 部署的 Qwen3 Embedding 4B。

本任务先按 64K 上下文预算重构主 Agent，不立即切换当前本地 Embedding。

建议主 Agent单次上下文预算：

```text
系统提示词和Schema：约 5K
不超过30条规则：约 8～12K
分类检索片段：约 20～25K
项目、文件摘要和资料目录：约 2～4K
工具历史和输出预留：约 6K
最终输出预留：约 8K
```

输入目标控制在约 45K～50K，不以填满 64K 为目标。

后续切换 vLLM 时应保持：

- 模型 URL、Key 和模型名只通过配置修改。
- `enable_thinking` 等非标准参数可配置且可关闭，避免服务不支持时请求失败。
- Embedding 模型或维度变化后删除旧索引并全量重建。

## 12. 测试设计

### 12.1 规则抽取

- 多批次规则按六类增量抽取。
- 下一批只接收精简规则目录，不接收全部历史规则。
- 最终规则总量不超过 30。
- 不设置分类上限、分类下限和优先级数量配额。
- 同类技术参数合并为复合规则。
- `fatal` 规则必须校正为 `critical`。
- `evidence_required=true` 必须校正为 `evidence_check`。

### 12.2 投标文件摘要和路由

- 红外热成像仪文件返回 `matched` 并建立索引。
- 机械加工设备文件返回 `not_matched`，不建立投标索引、不进入主 Agent。
- `uncertain` 文件不建立投标索引、不进入主 Agent，生成文件级人工复核结果。
- 低置信度或理由不足的路由结果规范化为 `uncertain`。
- `not_matched` 和 `uncertain` 文件仍生成完整 `FileAuditResult`。
- 摘要路由每个文件只调用一次模型。
- 摘要包含项目、投标方、包号、物资、产品、型号、分类概览和关键章节等清洗结果。

### 12.3 资料分类

- 每份资料只调用一次分类模型。
- 分类结果同时包含 `catalog_profile` 和 `retrieval_profile`。
- `catalog_profile` 能正确映射到规则分类并聚合为主 Agent资料目录。
- `retrieval_profile` 保存资料自身关键词、实体和可搜索事实。
- 两种视图均通过同一个 prompt-only JSON Schema 校验。

### 12.4 主 Agent

- 一个相关文件的全部规则一次进入主 Agent。
- State 中不再存在逐规则执行游标。
- 批量 Decision必须覆盖全部规则。
- 普通规则不自动回查招标原文或调用资料子 Agent。
- 对应资料目录为空时不调用子 Agent，并记录缺失原因。
- 主 Agent使用可配置轮数上限，默认建议为 8。
- 信息充分时主 Agent必须提前结束，不机械执行满轮数。

### 12.5 资料核验

- 主 Agent可根据规则分类看到同名资料目录。
- Claim 包含精确关键词和核验点。
- 子 Agent最多 3 轮。
- 子 Agent第一轮检索、第二轮回查、第三轮返回结果。
- 子 Agent不得访问其他 bidder 的资料。
- 输出不包含候选列表和内部消息历史。

### 12.6 统一结构化输出

- 所有业务结构化模型结果使用 `prompt_only`。
- 每个提示词明确注入自己的输出 Schema，不能复用含义模糊的通用 `output_schema`。
- 模型输出只修复一次，修复失败后按对应阶段错误策略处理。
- Agent工具调用继续使用 LangChain标准 `tool_calls`。

### 12.7 输出一致性

- JSON 中所有上传文件均有独立结果。
- Word 文件数量与 JSON 中的 `FileAuditResult` 数量完全一致。
- 不相关文件在 Word 中显示摘要和排除理由。
- Word 不自行过滤 Finding、EvidenceReviewResult 或不适用文件。
- Word 重新生成不改变 JSON。

### 12.8 性能验收

记录每个审核任务：

- 摘要路由模型调用次数。
- 主 Agent模型调用次数。
- 子 Agent调用次数和平均轮数。
- Chat输入/输出 Token。
- 投标索引构建耗时。
- 单文件审核耗时。

三文件测试集的目标调用结构：

```text
摘要和路由：3 次
相关文件主 Agent：每个文件按需执行，受可配置上限约束
资料子 Agent：仅按实际重点 Claim 调用，每次最多 3 轮
```

不得再出现 `文件数 × 规则数` 个主 Agent工作单元。

## 13. 验收标准

- 最终 RuleSet 不超过 30 条并按六类组织，不设置规则数量下限。
- 规则只设置总量上限 30，不设置分类或优先级数量配额。
- 每条规则具有 `priority` 和 `verification_level`。
- 投标文件在建立索引前完成一次详细数据清洗摘要和相关性路由。
- 路由为 `not_matched` 的文件不建立投标索引、不进入主 Agent，但完整进入 JSON 和 Word。
- 路由为 `uncertain` 的文件不建立投标索引、不进入主 Agent，直接形成文件级人工复核结果。
- 每个相关文件只建立一个批量主审核工作单元。
- 主 Agent能看到项目摘要、文件摘要、全部分类规则、分类检索片段和精简资料目录。
- 主 Agent轮数上限可配置，资料子 Agent最多运行 3 轮。
- 资料目录分类与规则分类一致，底层仍使用细粒度 `EvidenceType` 检索过滤。
- 每份投标方资料一次分类同时生成 `catalog_profile` 和 `retrieval_profile`。
- 所有业务结构化模型结果统一使用 prompt-only JSON。
- 重点规则按需回查原文或核验资料，普通规则默认只做低成本投标响应审核。
- 最终结果由代码确定性汇总，JSON 和 Word 内容一致。
- 三文件测试集可以在可接受时间内完成，不再出现数百个逐规则 Agent调用。
