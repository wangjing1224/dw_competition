# 任务 16：规则准入与审核上下文瘦身重构

## 1. 目标

在任务 15 已完成“按文件批量审核”的基础上，解决真实比赛数据暴露出的三个核心问题：

1. 规则抽取没有定义“什么内容有资格成为投标审核规则”，导致合同履约、开标评标、平台操作等无关事项进入最终规则。
2. 给主 Agent 的上下文过重，规则、资料、检索片段和 Schema 重复堆叠，真实 Trace 中主 Agent 输入达到 107K Token。
3. 主 Agent 直接输出完整业务 JSON，导致输出被截断，代码无法稳定拼接报告。

本任务不推翻现有六类规则体系、主 Agent、资料子 Agent 和最终报告结构。核心调整是：

- 保留一个单一 RuleSet，不再区分“轻量规则库”和“重量规则库”。
- 完整 RuleSet 继续保存业务字段和来源元数据。
- 给模型看的 RuleSet 投影只保留审核判断需要的核心字段，不额外维护第二套规则库。
- 规则抽取改为“当前 RuleSet + 当前招标文件批次 -> 增量操作”。
- 招标原文、投标文件、资料文件都通过向量召回 + rerank 检索，不给模型暴露底层来源 chunk 映射。
- 主 Agent 输出分类总结和规则级短结论，完整 JSON 由代码确定性拼接。
- 图片型资料不接 OCR，明确进入人工核验路径。

完成后应达到：

- 最终有效规则通常为 15～25 条，硬上限 30 条，不设置下限和分类配额。
- 规则覆盖资格、商务、技术、履约能力、一致性风险等核心审核点。
- 重要招标文件可以提取多条规则，不重要文件允许只提取少量规则或零条规则。
- 合同履约、开标异议、评标澄清、授标排序、平台上传状态等非投标审核事项不进入主 Agent。
- 主 Agent 正常输入目标控制在 20K～35K Token。
- 主 Agent 最终输出目标控制在 5K～6K Token，输出上限设置为 16384。
- 最终完整 `AuditResult`、精简后的 `Finding` 和 Word 报告仍由领域模型承载。

## 2. 当前问题依据

### 2.1 规则抽取结果失真

真实数据 `data/parsed/rules/project-1.json` 中：

- 最终保存 30 条规则，但规则编号最高达到 `rule-49`，说明截断前至少生成了 49 条。
- 30 条全部为 `critical`。
- 28 条为 `fatal`。
- 资格类规则达到 16 条。
- 技术类只有 1 条泛化规则，没有形成红外热成像仪的具体技术审核组。
- 最终规则主要来自前两个来源文件，其余技术规范、货物清单等重要文件被截断策略挤出。
- 多条规则属于开标、评标、授标或合同履约阶段，无法通过当前投标文件审核。

根因不是单纯“数量上限不对”，而是规则准入标准缺失。

### 2.2 规则抽取 Trace 显示无效产物很多

- 大部分内容是履约保证金、迟延交货、违约金、合同解除和通知送达等履约阶段事项。

这说明“只给已有规则标题”无法有效约束模型，也无法完成可靠去重。

## 4. 规则体系

### 4.1 六类规则保持不变

继续使用：

```text
format
qualification
commercial
technical
performance_capacity
consistency_risk
```

六类用于：

- 组织最终 RuleSet。
- 生成投标文件摘要。
- 构造主 Agent 输入。
- 输出分类级审核总结。
- 辅助资料目录和资料核验。

六类不是规则数量配额。某类可以没有规则，也可以根据项目特点包含较多规则。

### 4.2 最终规则数量

```text
推荐范围：15～25 条
硬上限：30 条
下限：无
分类上限：无
分类下限：无
```

数量控制发生在规则归并之后，不能再按来源文件顺序直接截断。

### 4.3 完整 RuleSet 与模型投影

系统只维护一个完整 RuleSet。完整规则仍然保存来源、状态等业务和溯源字段，供代码生成最终
JSON、Word 和来源回查；这些字段不需要重复发送给 LLM。

给 LLM 的规则投影只包含：

```python
class RuleItem(StrictModel):
    rule_id: str
    category: RuleCategory
    requirement: str
    priority: RulePriority
    verification: VerificationMode
    evidence_types: list[EvidenceType] = []
```

字段含义：

| 字段 | 含义 |
|---|---|
| `rule_id` | 递增短 ID，例如 `rule-1`，用于模型轻量引用和代码拼接 |
| `category` | 六类之一 |
| `requirement` | 审核要求正文，直接用于展示和检索 |
| `priority` | 重要性，例如 `critical`、`important`、`normal` |
| `verification` | 核验方式：`bid_only`、`source_check`、`evidence_check`、`cross_check` |
| `evidence_types` | 需要资料核验时的资料类型范围 |

完整 RuleSet 可以继续维护，但不要求模型看见或输出：

- `name`
- 完整 `SourceRef`
- `supporting_sources`
- `project_id`
- `task_id`
- `bidder_id`
- `status`
- 完整身份字段
- 完整 JSON Schema

`name` 对模型没有必要；报告展示可以直接使用 `requirement` 的短标题截断版，或由代码从
`requirement` 生成展示标题。`source/supporting_sources` 等来源信息由代码根据当前文件和章节
绑定在完整 RuleSet 中，通过 `rule_id` 与模型投影对应。

这不是“轻量规则库 + 重量规则库”两套数据，而是：

```text
完整 RuleSet
  -> 持久化、报告、来源回查

present_rules_for_model(RuleSet)
  -> 调用时临时生成的精简视图
```

### 4.4 `evidence_types` 的作用

`evidence_types` 用于告诉主 Agent 和资料子 Agent：

```text
这条规则如果需要资料核验，优先检索哪些资料类型。
```

示例：

```json
{
  "rule_id": "rule-3",
  "category": "qualification",
  "requirement": "投标人应提供有效营业执照并证明主体资格合法",
  "priority": "critical",
  "verification": "evidence_check",
  "evidence_types": ["business_license"]
}
```

它不是检索关键词，也不是证据结论。实际资料能否核验，还要看资料是否存在、是否可读、
检索是否命中，以及子 Agent 的核验结果。

### 4.5 规则准入原则

只有满足以下条件的内容，才有资格进入最终 RuleSet：

1. 来源中存在明确要求，不是背景介绍、目录标题或一般说明。
2. 要求能够在当前投标审核阶段形成结论。
3. 结论至少能够通过以下一种方式获得：
   - 投标文件正文或表格。
   - 投标方支撑资料。
   - 当前任务内多个投标文件或资料的一致性检查。
   - 必要时回查招标原文。
4. 要求对资格准入、实质响应、技术商务评审、风险识别或人工复核具有实际价值。
5. 规则能表达为简洁审核点，不与已有审核点高度重复。

以下内容默认不进入最终 RuleSet：

- 合同签订后的交货、验收、结算、违约金和合同解除事项。
- 开标异议、评标澄清、评标排序和授标规则。
- 只能由采购平台判断的上传时间、文件加密状态和系统操作状态。
- 必须依赖实时外部信用平台才能确认的失信、行贿、不良行为状态。
- 无法从当前投标文件、投标方资料或任务内数据得到结论的纯流程规则。

这些内容可以记录为调试日志，但不得占用最终 30 条规则。

## 5. 总体流程

```text
招标文件统一解析
  -> 建立招标文件索引
  -> 按章节/表格组成抽取批次
  -> 当前 RuleSet + 当前批次 -> LLM 输出 delta 操作
  -> 代码执行 add/merge；无有效增量时 operations 为空
  -> 全部批次完成后做确定性校验和稳定排序
  -> 得到单一最终 RuleSet

投标方资料
  -> 解析
  -> 资料类型分类
  -> 输出 classified / manual_review
  -> 建立 Evidence Index
  -> 按 evidence_type 生成主 Agent 资料目录
  -> 子 Agent 检索命中后读取对应 evidence_summary

投标文件
  -> 解析
  -> 建立投标文件索引
  -> 路由摘要：判断 matched / not_matched / uncertain
  -> not_matched / uncertain 直接进入 JSON 和 Word，说明理由
  -> matched 文件进入主 Agent
  -> 主 Agent 根据 RuleSet、投标摘要、资料目录按需调用工具
  -> 最终输出总体总结 + 分类总结 + 规则级短结论
  -> 代码按三类 chunk_ids 还原真实引用并生成 Finding、AuditResult
```

建索引不需要 LLM 参与。解析后的章节、段落和表格按现有 chunk 策略进入向量索引即可。

### 6.1 LLM 消息与 Markdown 模板约定

所有模型调用统一拆分为两类消息：

```text
SystemMessage
  -> 模型长期稳定的角色、任务边界、判断原则、工具使用策略和输出约束

HumanMessage
  -> 当前调用实际处理的项目、文件、规则、摘要、资料目录和核验任务等运行数据
```

两类消息都使用独立 Markdown 模板，不在 Python 中拼接大段不可见文本，也不为了方便查看而
把运行数据塞进 SystemMessage。

统一调用形式：

```python
messages = [
    SystemMessage(
        content=render_prompt(
            "bid_document_summary",
            output_schema=summary_schema,
        )
    ),
    HumanMessage(
        content=render_prompt(
            "bid_document_summary_input",
            project_profile=project_profile,
            rule_categories=rule_categories,
            document_context=document_context,
        )
    ),
]
```

约束：

- System 模板只放稳定指令，可以注入精简输出 Schema，但不注入整份业务文档。
- Human 模板使用 Markdown 组织章节，并在需要精确结构时嵌入精简 JSON。
- 规则抽取、资料分类、投标摘要、主 Agent 和资料子 Agent 全部遵循相同约定。
- `AIMessage` 和 `ToolMessage` 继续由 LangGraph 消息历史维护，不写进静态模板。
- 工具的名称、描述和参数 Schema 继续由 `bind_tools` 注入，System 模板只写工具使用原则。
- Trace 中应能直接区分稳定指令和本次运行数据，便于排查上下文膨胀。
- 本任务后续再分别精简各调用的输入 DTO 和输出 JSON Schema；消息拆分本身不代表继续使用
  当前完整领域 Schema。

## 7. 规则抽取重构

### 7.1 输入：当前 RuleSet + 当前批次

不再给模型只看 `existing_outline` 的标题列表，而是给它看当前精简 RuleSet：

```json
[
  {
    "rule_id": "rule-1",
    "category": "qualification",
    "requirement": "投标人应为依法注册并有效存续的法人或其他组织",
    "priority": "critical",
    "verification": "evidence_check",
    "evidence_types": ["business_license"]
  }
]
```

然后给当前招标文件批次：

```markdown
# 当前来源

- 文件：技术规范书-脱敏.docx
- 批次：1/1

## 章节 section-123

### 标题

4.2 技术性能要求

### 内容

……
```

DeepSeek-V4-Flash 长上下文环境下，30 条以内的当前 RuleSet 投影可以完整输入。这样模型能判断：

- 当前批次是否产生新增规则。
- 新内容应合并到已有哪条规则。
- 当前内容是否对已有规则形成有效补充。
- 当前内容是否没有有效增量，此时不输出操作。

### 7.2 输出：delta 操作

模型不输出完整最终 RuleSet，只输出增量操作：

```python
class RuleDeltaOperation(StrictModel):
    action: Literal["add", "merge"]
    rule_id: str | None = None
    category: RuleCategory | None = None
    requirement: str | None = None
    priority: RulePriority | None = None
    verification: VerificationMode | None = None
    evidence_types: list[EvidenceType] = []
    reason: str
```

字段说明：

- `add`：新增审核规则，必须提供 `category/requirement/priority/verification`。
- `merge`：合并到已有规则，必须提供 `rule_id`，可提供更优 `requirement`。

以下情况不输出操作，直接返回空 `operations`：

- 当前批次没有符合准入标准的投标审核规则。
- 当前内容已经被现有规则完整覆盖，没有新增信息。
- 当前内容只是背景、流程、履约或其他非投标审核事项。

`reason` 用于调试，不进入主 Agent。

### 7.3 规则字段长度

```text
requirement：建议 40～160 个中文字符
reason：建议 20～80 个中文字符
单批 add 数量：根据内容决定，不设下限
```

技术参数不要按每个表格单元拆成独立规则。优先按审核主题合并，例如：

```text
红外热成像仪成像、测温精度、热灵敏度、接口和防护等级应满足技术规范。
```

### 7.4 核心伪代码

文件：`app/rules/extractor.py`

```python
async def extract_rules_incrementally(project_id, parsed_documents):
    rule_set = RuleSet(project_id=project_id, rules=[])

    for document in parsed_documents:
        for batch in build_rule_extraction_batches(document):
            prompt = render_rule_extraction_prompt(
                current_rules=present_rules_for_model(rule_set),
                document=document,
                batch=batch,
            )
            operations = await invoke_json_only(
                model=rule_extraction_model,
                prompt=prompt,
                output_model=RuleDeltaResult,
            )
            rule_set = apply_rule_delta_operations(
                rule_set=rule_set,
                document=document,
                batch=batch,
                operations=operations,
            )

    return finalize_rule_set(rule_set, maximum=30)
```

这里是串行增量，因为每批依赖当前 RuleSet。后续如要并发，只能按文件先抽候选再全局归并；
当前优先保证去重和准入质量。

### 7.5 代码执行 delta

文件：`app/rules/merger.py`

```python
async def apply_rule_delta_operations(rule_set, document, batch, operations):
    for op in operations.items:
        op = normalize_priority_verification(op)
        validate_rule_operation(op, rule_set)

        if op.action == "add":
            if not passes_rule_admission(op):
                log_ignored_rule_candidate(document, batch, op.reason)
                continue
            rule_set.rules.append(
                RuleItem(
                    rule_id=next_rule_id(rule_set),
                    category=op.category,
                    requirement=normalize_requirement(op.requirement),
                    priority=normalize_priority(op.priority),
                    verification=op.verification,
                    evidence_types=op.evidence_types,
                )
            )
            bind_rule_source(
                rule_set=rule_set,
                rule_id=rule_set.rules[-1].rule_id,
                document=document,
                batch=batch,
            )
            if len(rule_set.rules) > 30:
                rule_set = await resolve_rule_capacity(
                    rule_set=rule_set,
                    document=document,
                    batch=batch,
                    maximum=30,
                )
            continue

        if op.action == "merge":
            rule = get_rule(rule_set, op.rule_id)
            rule.requirement = merge_requirement(rule.requirement, op.requirement)
            rule.priority = max_priority(rule.priority, op.priority)
            rule.verification = max_verification(
                rule.verification,
                op.verification,
            )
            rule.evidence_types = merge_evidence_types(
                rule.evidence_types,
                op.evidence_types,
            )
            append_supporting_source(
                rule=rule,
                document=document,
                batch=batch,
            )

    return rule_set
```

在执行 `add/merge` 前，代码先校验字段完整性和重要程度、核验方式的组合。

重要程度：

```text
critical  = 关键，可能导致废标或重大风险
important = 重要，影响实质响应或审核结论
normal    = 普通，一般响应和完整性要求
```

核验方式：

```text
bid_only       = 只检查投标文件
source_check   = 必要时回查招标文件原文
evidence_check = 核验投标方支撑资料
cross_check    = 在投标文件、招标文件或支撑资料之间交叉核对
```

第一版只确定性修正以下不合理组合：

```text
normal + evidence_check -> important + evidence_check
normal + cross_check    -> important + cross_check
```

原因是需要启动资料子 Agent 或交叉核对的规则不应仍标记为普通。代码保留核验方式，只把重要
程度提升为“重要”，并记录原值、修正值和原因，不因为模型单个字段判断偏差而丢弃有效规则。

其他组合不做强制限制。例如“最高限价”可以是 `critical + bid_only`，因为它虽然关键，但可以
直接通过投标报价判断。

`merge` 不允许降低已有规则的重要程度或核验深度。合并时保留已有规则与新增信息中的较高
重要程度，同时合并 `verification/evidence_types`，并把当前文件和章节追加为完整规则的支撑
来源。

只有以下情况才拒绝当前操作：

- 缺少 `requirement` 等必要字段。
- `merge` 引用了不存在的 `rule_id`。
- 字段值不属于允许枚举。
- `add` 内容不满足规则准入条件。

### 7.6 超限时的容量合并

规则达到30条后，后续文件仍然允许产生 `add`。当一次新增使规则总量超过30条时，才触发一次
容量合并调用：

```text
当前完整规则的模型投影
+
本批新增规则
+
当前文件内容
→ LLM只判断哪些规则可以合并
→ 输出 merge 操作
→ 代码执行合并并重新计数
```

该调用不是每个项目结束后的固定全局整理，只在规则超限时触发。模型不能新增规则，只能把
语义相近、审核目标一致的规则合并，从而避免前面文件先占满30条后，后续技术规范无法进入。

```python
async def resolve_rule_capacity(rule_set, document, batch, maximum):
    operations = await invoke_capacity_merge(
        current_rules=present_rules_for_model(rule_set),
        current_document=batch,
    )
    rule_set = apply_merge_operations(rule_set, operations)
    ensure_rule_count(rule_set, maximum=maximum)
    return rule_set
```

如果一次容量合并后仍超过30条，记录明确错误并停止规则生成，不能按照文件顺序静默丢弃当前
新增规则，也不能由代码任意截断某条规则。

### 7.7 最终确定性校验

规则抽取按批次严格串行，每个批次都看到最新 RuleSet，因此全部批次完成后不再调用 LLM 做
第二次全局整理，也不再重新合并、改写或按价值截断规则。

最终代码只执行：

1. 校验 `rule_id` 唯一。
2. 校验所有必要字段完整。
3. 再次校验并标准化重要程度与核验方式组合。
4. 按六类、重要程度和 `rule_id` 稳定排序。
5. 确认规则总量不超过 30 条。

```python
def finalize_rule_set(rule_set):
    validate_unique_rule_ids(rule_set)
    validate_required_fields(rule_set)
    normalize_and_validate_priority_verification(rule_set)
    ensure_rule_count(rule_set, maximum=30)
    return stable_sort(
        rule_set,
        by=["category", "priority", "rule_id"],
    )
```

30条限制通过超限时的容量合并维持；最终数量校验只是保险，不在最后任意删除已经形成的规则。

但不要在业务代码或任务文档中写死 `requirement + question` 这种拼接规则。

```python
class SearchTenderSourceTool(BaseTool):
```

## 9. 投标文件摘要与路由

### 9.1 摘要节点职责

投标文件摘要节点不只是写一段摘要，还承担数据清洗和路由职责：

1. 判断投标文件是否与当前项目相关。
2. 如果不相关或不确定，输出结构化理由，直接进入最终 JSON 和 Word。
3. 如果相关，产出能供主 Agent 审核使用的结构化事实。

### 9.2 路由结果

```python
class BidRouteStatus(StrEnum):
    MATCHED = "matched"
    NOT_MATCHED = "not_matched"
    UNCERTAIN = "uncertain"
```

处理规则：

- `matched`：进入主 Agent。
- `not_matched`：不进入主 Agent，输出不适用理由。
- `uncertain`：不进入主 Agent，输出“项目相关性不确定，需要人工审核”的理由。

这里的 `uncertain` 是大路由不确定。它和主 Agent 内部某条规则的“小不确定”不同。

### 9.3 摘要输出

摘要节点输入只包含：

- 项目概况，例如项目名称、采购对象、标包信息、关键物资或设备名称。
- 六类审核方向的名称和一句话说明。
- 投标文件解析文本。
- 路由和摘要输出要求。

不输入完整 RuleSet，也不输入每条规则。摘要节点的职责是判断项目相关性并提炼文件事实，
不是提前执行规则审核。摘要质量应通过输出 schema 和提示词约束解决，而不是靠把全部规则塞进去。

模型只输出三个字段：

```python
class BidDocumentSummary(StrictModel):
    match_status: BidRouteStatus
    match_reason: str
    summary: str
```

示例：

```json
{
  "match_status": "matched",
  "match_reason": "项目名称、采购对象和红外热成像仪型号均与当前项目一致。",
  "summary": "## 文件基本信息\n投标人为某某科技有限公司，响应红外热成像仪包1……\n\n## 资格与商务事实\n……\n\n## 技术响应事实\n……\n\n## 履约能力与业绩\n……\n\n## 明确缺失或待核验信息\n……"
}
```

字段职责：

- `match_status`：只供程序路由。
- `match_reason`：解释 `not_matched/uncertain` 或记录匹配依据，进入最终 JSON 和 Word；
  不传给主 Agent。
- `summary`：匹配文件的详细清洗结果，是传给主 Agent 的核心投标上下文。

`file_id`、任务身份和文件身份由代码关联，不要求模型重复输出。

`summary` 虽然是一个字符串，但内部使用稳定 Markdown 层级，至少覆盖：

- 文件基本信息。
- 资格和商务事实。
- 技术响应事实。
- 履约能力与业绩。
- 一致性风险。
- 明确缺失或待核验信息。

对于 `matched`，重点约束 `summary` 的事实密度；对于 `not_matched/uncertain`，重点约束
`match_reason` 的事实依据。摘要节点看到解析后的投标文件全文或大块上下文，应尽量提炼明确
主体、产品、型号、参数、金额、日期和声明，避免只写“包含技术响应”等泛化描述。

## 10. 资料分类与资料目录

### 10.1 资料分类输出

资料分类器只判断“这是什么资料、是否可以自动使用、资料主要包含什么”，不理解 RuleSet，
也不判断资料服务哪一类规则。

```python
class EvidenceClassification(StrictModel):
    evidence_type: EvidenceType
    classification_status: ClassificationStatus
    reason: str
    bid_summary: str
    evidence_summary: str
```

字段职责：

- `evidence_type`：资料类型，用于主 Agent 选择资料和工具层强制过滤。
- `classification_status`：`classified/manual_review`；低置信度或正文不可可靠读取时直接
  `manual_review`，不再额外输出数值置信度。
- `reason`：说明分类或人工复核原因，保存到最终 JSON/Word；不传给主 Agent 或资料子 Agent。
- `bid_summary`：给主 Agent 看的单文件简短资料说明。
- `evidence_summary`：资料检索命中后给资料子 Agent 看的较详细候选摘要。

示例：

```json
{
  "evidence_type": "business_license",
  "classification_status": "classified",
  "reason": "正文可识别为企业营业执照",
  "bid_summary": "已提供营业执照，可用于核验投标主体资格",
  "evidence_summary": "营业执照显示主体为某某公司，正文包含统一社会信用代码等企业登记信息"
}
```

删除现有模型可见字段：

- `confidence`
- `catalog_profile`
- `retrieval_profile`
- `rule_categories`
- `entities`
- `keywords`
- `searchable_facts`
- `verifiable_topics`

检索 query 和关键词由资料子 Agent 根据核验任务及摘要动态生成，不要求资料分类模型提前维护
另一套检索关键词。

### 10.2 图片资料处理

第一版规则：

- 可以识别资料类型。
- 不生成证书编号、主体、日期和有效期等未读取事实。
- 不进入可自动核验的正文候选。
- `classification_status` 直接设为 `manual_review`。
- 主 Agent 看到资料目录中的 `manual_review` 后，不再调用资料子 Agent。
- 最终 JSON 和 Word 标记“资料存在，但图片内容需人工核验”。

### 10.3 主 Agent 资料目录

资料分类以原始资料文件为单位，每个文件只调用一次分类 LLM。分类完成后，文件正文再按现有
策略切片、Embedding 并建立 Evidence Index。

代码只按 `evidence_type` 对文件级分类结果分组，不再调用 LLM 生成类型级聚合摘要：

```json
{
  "business_license": [
    {
      "file_id": "file-10",
      "status": "classified",
      "summary": "营业执照，可用于核验投标主体资格"
    }
  ],
  "contract": [
    {
      "file_id": "file-12",
      "status": "classified",
      "summary": "国网河北红外热成像仪供货合同"
    },
    {
      "file_id": "file-13",
      "status": "classified",
      "summary": "国网山东红外热成像仪供货合同"
    }
  ],
  "certificate": [
    {
      "file_id": "file-14",
      "status": "classified",
      "summary": "产品认证证书，可自动核验"
```

每个数组元素直接来自该文件的分类结果：

- `file_id`：代码补充，用于区分同类型的多个资料文件。

- `summary`：该文件自己的 `bid_summary`。

主 Agent 看到这个目录后，可以判断：

- RuleSet 的 `evidence_types` 所需资料是否存在。
- 哪些具体文件为 `classified`，值得调用资料子 Agent。
- 哪些具体文件为 `manual_review`，应直接形成规则级人工复核结论。
- 对应资料类型不存在时不调用资料子 Agent。

### 10.4 资料子 Agent 可见视图

主 Agent 调用资料核验工具时只填写两个参数：

字段职责：

- HumanMessage 中的 `file_id/evidence_summary`：帮助子 Agent 判断优先检索哪些文件以及如何组织

`manual_review` 文件不进入自动检索候选。工具不返回全量资料、不返回其他资料类型，也不重复
提供完整 `SourceRef`。

### 11.1 消息分层

主 Agent 的两层消息为：

### 11.2 主 Agent HumanMessage：Markdown 主结构 + 精简 JSON

下面的完整内容对应 `configs/prompts/templates/bid_agent_input.md`，渲染后作为一个
`HumanMessage` 发送给主 Agent：


示例：

````markdown

投标人为某某科技有限公司，响应红外热成像仪包1，投标产品型号为XXX-640。

### 资格与商务事实

投标文件声明已提供营业执照、法定代表人证明、报价表和商务偏差表。当前摘要未确认营业执照
````

## 12. 主 Agent 工具策略

### 12.1 不强制固定阶段

主 Agent 保留自主判断：

```text
摘要、规则和资料目录足够
  -> 直接输出最终轻量审核结果

重点规则信息不足
  -> 按需调用一个或多个工具
  -> 获取结果后继续判断
  -> 最终输出轻量审核结果
```

简单标书能够直接判断时，不应为了流程形式强制调用工具。

### 12.2 三类工具

1. 投标文件回查：
   - 摘要不足以判断某条重点规则。
   - 重点规则需要更精确响应内容。
   - query 由主 Agent 根据规则和摘要动态生成。
2. 招标原文回查：
   - 规则要求、适用范围或重要性不清楚。
   - query 由主 Agent 根据当前疑问动态生成。
   - 底层统一走向量召回 + rerank。
3. 投标方资料核验：
   - 规则为 `evidence_check`。
   - 资料目录显示对应 `evidence_types` 存在且正文可读。
   - 子 Agent 最多三轮。

工具的具体 `name`、`description` 和参数说明放在 LangChain `BaseTool` / `bind_tools`
里维护，不在 `bid_agent.md` 里重复写一遍。主 Agent 提示词只保留工具使用原则，避免系统提示词
和工具描述重复膨胀。

### 12.3 检索工具内部职责

`RetrievalService` 只提供通用的向量召回、关键词召回和 rerank。具体 BaseTool 负责当前业务
场景的完整检索收口：

1. 根据当前任务状态构造 `project_id/bidder_id/task_id/file_id/evidence_type` 等过滤条件。
2. 接收 Agent 提供的一个或多个 query。
3. 分别调用 `RetrievalService.search()`。
4. 多 query 结果按 `chunk_id` 合并去重。
5. 按 rerank 分数保留最终 `top_k`。
6. 限制单个片段和本次 ToolMessage 的总字符数。
7. 返回精简片段，不暴露内部检索分数和重复来源对象。

统一精简返回结构：

```json
{
  "chunks": [
    {
      "chunk_id": "chunk-evidence-18",
      "file_id": "file-10",
      "section": "营业执照登记信息",
      "content": "名称：某某科技有限公司；统一社会信用代码：……"
    }
  ]
}
```

工具不同时返回 `content` 和内容相同的 `source.quote`，也不返回完整 `SourceRef`。实际使用的
片段由 Agent 在最终结果中按来源类型填写到 `tender_chunk_ids/bid_chunk_ids/evidence_chunk_ids`。
代码直接根据 chunk ID 从对应索引恢复完整来源，不增加额外引用映射层。

各工具的业务过滤边界：

```text
投标文件检索：task_id + 当前 bid_file_id
招标原文检索：project_id + document_role=tender
资料检索：bidder_id + evidence_type，可选 file_id
```

不再设置独立的 `app/audit/retrieval_context.py`。去重、预算和 ToolMessage DTO 都由具体工具
维护，避免检索结果在服务、上下文模块和工具之间重复加工。

### 12.4 子 Agent 输入

主 Agent 调用资料子 Agent 时，向工具提交当前规则、核验要求和一个资料类型：

```python
class EvidenceReviewToolInput(StrictModel):
    rule_id: str
    verification_request: str
    evidence_type: EvidenceType
```

示例：

```json
{
  "rule_id": "rule-3",
  "verification_request": "核验营业执照主体是否与投标人一致，证照信息是否支持主体资格要求",
  "evidence_type": "business_license"
}
```

`verification_request` 必须明确：

- 需要确认什么事实。
- 需要比较哪些主体、产品、型号、数量、日期或有效期。
- 什么条件下可以支持当前审核要求。
- 不要展开无关资料。
- 找不到或不可读时直接返回不可核验原因。

`rule_id` 由主 Agent填写，但工具构造子 Agent HumanMessage时不注入该字段。子 Agent只看到
核验要求、资料类别和文件摘要，不感知当前规则 ID。工具在子 Agent完成后把 `rule_id` 重新挂到
统一引用记录上。

当前投标文件、投标方和任务身份继续由主图、工具和子图状态维护，不要求主 Agent 填写。

工具层必须使用当前 `bidder_id + evidence_type` 做强制数据过滤。子 Agent 只做资料核验，
不重新审核整个投标文件，也不能查看其他投标方或未授权资料类型。

### 12.5 子 Agent 轻量输出

资料子 Agent 不再返回完整身份字段和完整 `SourceRef`，最小输出为：

```python
class EvidenceReviewDecision(StrictModel):
    status: EvidenceReviewStatus
    summary: str
    evidence_chunk_ids: list[str] = []
```

示例：

```json
{
  "status": "supported",
  "summary": "营业执照主体与投标人一致，已找到能够支持主体资格声明的登记信息。",
  "evidence_chunk_ids": ["chunk-evidence-18"]
}
```

保留的状态：

```text
supported
partially_supported
unsupported
contradicted
ocr_required
unverifiable
```

删除 `weakly_related`；弱相关资料不能支持当前核验任务，应归入 `unsupported` 或
`unverifiable`。

不能只返回一个自然语言字符串，因为工具和代码仍需要稳定判断支持状态，并根据
`evidence_chunk_ids` 恢复子 Agent实际使用的资料原文。

资料核验工具最终返回给主 Agent：

```json
{
  "rule_id": "rule-3",
  "status": "supported",
  "summary": "营业执照主体与投标人一致，登记信息支持主体资格要求。",
  "evidence_chunk_ids": ["chunk-evidence-18"]
}
```

`rule_id` 由工具重新挂回结果，子 Agent不感知该字段。主 Agent把资料核验结论写入规则
`summary.reason`，把实际使用的片段写入 `evidence_chunk_ids`。

## 13. 主 Agent 轻量输出

### 13.1 分类总结 + 规则短结论

模型不再输出完整 `Finding`，只输出：

```python
class RuleAuditSummary(StrictModel):
    reason: str
    tender_chunk_ids: list[str] = []
    bid_chunk_ids: list[str] = []
    evidence_chunk_ids: list[str] = []


class RuleAuditDecision(StrictModel):
    rule_id: str
    result: FindingResult
    summary: RuleAuditSummary


class CategoryAuditDecision(StrictModel):
    category: RuleCategory
    summary: str
    rules: list[RuleAuditDecision]


class AgentAuditDecision(StrictModel):
    summary: str
    categories: list[CategoryAuditDecision]
```

长度目标：

```text
总体 summary：建议 200～500 字，最大 800 字
分类 summary：建议 100～300 字，最大 500 字
单条 rule summary.reason：建议 30～100 字，最大 200 字
```

最终报告中如需展示规则正文、类别、优先级、证据类型、来源等，由代码按 `rule_id` 从 RuleSet
拼接。

`summary.reason` 是该规则的完整简短审核结论，不限制为单纯的“原因”。它可以说明投标响应、
资料核验结论、缺失信息和人工复核建议。

三个 chunk ID 字段均为可选：

- `tender_chunk_ids`：实际使用的招标文件原文片段。
- `bid_chunk_ids`：实际使用的投标文件原文片段。
- `evidence_chunk_ids`：实际使用的投标方资料原文片段。

没有使用对应工具结果时可以省略该字段或保持空数组。

示例：

```json
{
  "rule_id": "rule-3",
  "result": "compliant",
  "summary": {
    "reason": "营业执照主体与投标人一致，登记信息能够支持主体资格要求。",
    "evidence_chunk_ids": ["chunk-evidence-18"]
  }
}
```

### 13.2 最终 Finding

`Finding` 只表示最终报告中“一条规则的审核结果”，不再强制拆分
`rule_source/bid_source/evidence_result_id`：

```python
class Finding(StrictModel):
    rule_id: str
    result: FindingResult
    summary: str
    tender_chunk_ids: list[str] = []
    bid_chunk_ids: list[str] = []
    evidence_chunk_ids: list[str] = []
```

Finding 与主 Agent 的三类 chunk ID字段保持一致，不再增加额外映射层。JSON和Word生成时根据
chunk ID从对应索引读取真实文件、章节和原文。

没有调用工具时：

```json
{
  "rule_id": "rule-5",
  "result": "compliant",
  "summary": "投标报价未超过最高限价。",
  "tender_chunk_ids": [],
  "bid_chunk_ids": [],
  "evidence_chunk_ids": []
}
```

三个字段都为空也是合法结果，不伪造来源。

### 13.3 生成最终 Finding

文件：`app/graph/state_updates.py`

```python
def materialize_findings(state, decision):
    rules = {rule.rule_id: rule for rule in state["rule_set"].rules}

    findings = []
    for category in decision.categories:
        for item in category.rules:
            rule = rules[item.rule_id]
            findings.append(
                Finding(
                    rule_id=rule.rule_id,
                    result=item.result,
                    summary=item.summary.reason,
                    tender_chunk_ids=item.summary.tender_chunk_ids,
                    bid_chunk_ids=item.summary.bid_chunk_ids,
                    evidence_chunk_ids=item.summary.evidence_chunk_ids,
                )
            )

    ensure_every_rule_exactly_once(findings, rules)
    return findings
```

规则正文、分类、重要程度等信息通过 `rule_id` 从完整 RuleSet 获取，不需要在 Finding 中重复
保存。没有使用工具时，三个 chunk ID数组都为空。

### 13.4 JSON 校验与一次受控重试

路由必须区分：

```text
有 tool_calls
  -> 执行工具

有合法 AgentAuditDecision
  -> 生成最终 Finding

finish_reason=length 或 JSON 明显截断
  -> 丢弃截断的 AIMessage，不加入正常消息历史
  -> 不重新执行已经完成的工具调用
  -> 追加一次要求压缩结果的 HumanMessage
  -> 最多重新生成一次完整 JSON

其他非法输出
  -> 使用现有 JSON 格式修复 HumanMessage
  -> 只修复字段、层级、枚举和 JSON 语法
  -> 最多修复一次
```

受控精简重答的 HumanMessage：

```text
上一次最终结果因输出长度限制被截断。

请基于已有审核上下文重新输出完整 JSON：
1. 不重复规则正文和来源内容；
2. 文件总体总结控制在500字以内；
3. 分类总结控制在300字以内；
4. 每条规则 summary.reason 控制在100字以内；
5. 每条规则只保留 rule_id、result、summary.reason 和实际使用的三类 chunk ID；
6. 必须完整覆盖全部规则并保证 JSON 闭合。

只返回 JSON，不要解释，不要重新调用工具。
```

如果受控精简重答或格式修复后仍然无法通过轻量 Schema 校验，则当前文件进入人工复核，并保存
具体校验错误。

主 Agent 配置：

```yaml
bid_chat_model:
  max_output_tokens: 16384
```

1M 上下文主要解决输入容量，`max_output_tokens=16384` 负责提供足够的结果输出空间。截断兜底
仍然保留，但不能再将残缺输出机械加入历史并反复调用。

## 15. 分阶段验证

不一次运行整条链路后再排查所有问题。开发完成后按三个阶段依次验证，上一阶段结果确认正确后
再进入下一阶段。

### 15.1 第一步：规则提取

只创建项目并上传招标文件，检查最终 RuleSet。

重点确认：

- 有效规则通常为15～25条，最多30条。
- 六类规则组织合理，技术规范和货物清单没有被忽略。
- 合同履约、开标评标和平台操作等非投标审核内容没有进入规则库。
- 相似要求通过 `merge` 合并，没有产生大量重复规则。
- 每条规则的 `requirement/priority/verification/evidence_types` 合理。
- 规则生成耗时、输入 Token 和输出 Token 可以接受。

这一阶段不上传投标方资料，也不运行审核 Agent。

### 15.2 第二步：资料分类

规则确认后，登记投标方并上传全部支撑资料，只检查资料分类和 Evidence Index。

重点确认：

- 每个原始资料文件只调用一次分类 LLM。
- `evidence_type/classification_status/reason/bid_summary/evidence_summary` 内容准确。
- 图片型或不可读资料正确进入 `manual_review`。
- 主 Agent 资料目录按 `evidence_type` 组织文件级列表。
- 文件级列表只包含 `file_id/status/summary`，没有二次摘要聚合。
- 可读资料正常完成切片、Embedding 和索引构建。

这一阶段不上传测试投标文件，也不运行主 Agent。

### 15.3 第三步：路由与 Agent

规则和资料分类确认后，再上传测试投标文件并创建审核任务。第三阶段分两部分观察。

#### 15.3.1 投标文件路由与摘要

- 相关文件输出 `matched` 和高质量详细摘要。
- 不相关文件输出 `not_matched` 和具体原因。
- 无法确定的文件输出 `uncertain` 并进入最终报告。
- `summary` 包含具体主体、产品、型号、参数、业绩和缺失信息，不是泛化描述。
- `not_matched/uncertain` 不进入主 Agent。

#### 15.3.2 主 Agent 与资料子 Agent

- 主 Agent 输入只有分组 RuleSet、投标摘要和文件级资料目录。
- 信息充分的简单规则允许直接判断。
- 信息不足时能够调用投标文件或招标原文检索工具。
- 需要资料核验时，主 Agent 传 `rule_id/verification_request/evidence_type`。
- `rule_id` 只由资料核验工具记录，不进入子 Agent HumanMessage。
- 子 Agent 根据文件摘要生成 query，通过检索工具获取原文并返回核验结果。
- 所有召回结果统一使用 chunk ID，并按招标文件、投标文件、投标方资料三个字段区分。
- 一条规则可以引用多个资料核验结果。
- 未调用工具时，最终 Finding 的三类 chunk ID字段为空，不伪造来源。
- 主 Agent 最终输出总体总结、分类总结和每条规则的简短结论。
- 完整 JSON 和 Word 能由代码正确拼接，特殊状态也不会被过滤。
- 主 Agent 输出未截断；若发生截断，只执行一次受控精简重答。

第三阶段通过后，再使用完整比赛数据进行一次全链路确认。

## 16. 实施顺序

### 第一步：RuleSet 瘦身与规则准入

- 保留完整 RuleSet 的业务和来源字段。

- 明确定义 `verification` 和 `evidence_types`。
- 增加规则准入策略。
- 去掉模型可见的 `name/source_chunk_ids/supporting_sources`。
- 建立 SystemMessage 与 HumanMessage 独立 Markdown 模板的统一加载方式。

### 第二步：规则抽取改为 delta 操作

- 修改 `rule_extraction.md`。
- 新增 `rule_extraction_input.md`，承载当前 RuleSet 和当前招标文件批次。
- 输入当前 RuleSet 和当前招标文件批次。
- 输出只包含 add/merge；没有有效增量时返回空 `operations`。
- 代码先标准化重要程度与核验方式，再执行规则变更。
- add/merge 时由代码绑定或追加完整规则来源。
- merge 同时合并 `priority/verification/evidence_types`，不能降低已有核验深度。
- 超过30条时触发一次容量合并，只允许模型输出 merge。
- 全部完成后只做 ID、字段、组合、数量校验和稳定排序。

### 第三步：投标摘要和路由

- 修改 `bid_document_summary.md`。
- 新增 `bid_document_summary_input.md`，承载项目概况、六类说明和投标文件解析内容。
- 输出仅保留 `match_status/match_reason/summary`。
- 使用一个详细 Markdown `summary` 承载匹配文件的具体事实。
- `not_matched/uncertain` 直接进入 JSON 和 Word。

### 第四步：资料分类和资料目录

- 资料分类改为 `evidence_type/classification_status/reason/bid_summary/evidence_summary`。
- 删除分类置信度、规则分类映射和独立 retrieval profile。
- 将资料分类稳定指令和本次文件输入拆成两个 Markdown 模板。
- 每个原始资料文件只分类一次，分类后再切片、Embedding 和建索引。
- 按 `evidence_type` 生成文件级 `file_id/status/summary` 列表，不做类型级摘要聚合。
- 检索命中后向资料子 Agent 提供文件级 `evidence_summary` 和 rerank 后的原文片段。

### 第五步：主 Agent 输入和工具

- 新增 `bid_agent_input.md`，不再由 Python 直接拼接整份 HumanMessage。
- 初始输入只包含 RuleSet、结构化摘要和资料目录。
- 在各 BaseTool 内完成业务过滤、多 query 合并、按 `chunk_id` 去重和返回预算控制。

  `source.quote`。

- 工具具体说明由 `BaseTool` / `bind_tools` 注入，提示词不重复维护。
- 主 Agent 根据规则、摘要和资料目录按需调用工具。
- 资料子 Agent 的核验任务使用独立 `evidence_subagent_input.md` 注入 HumanMessage。
- 资料核验工具参数包含 `rule_id/verification_request/evidence_type`，但 `rule_id` 不注入子 Agent。
- 工具将该类型下的 `file_id/evidence_summary` 列表注入子 Agent HumanMessage。
- 子 Agent 自行生成 query，原文片段由检索工具通过 ToolMessage 返回。
- 资料子 Agent 输出只包含状态、摘要和实际使用的 `evidence_chunk_ids`。
- 资料核验工具把 `rule_id` 挂到外层引用记录，子 Agent 不感知规则 ID。

- 截断时丢弃残缺输出并执行一次受控精简重答。

## 17. 验收标准

- 明确定义规则准入条件，非投标审核事项不进入主 Agent。
- 最终 RuleSet 通常为 15～25 条且不超过 30 条。
- 完整 RuleSet 保留业务和来源元数据，给 LLM 的临时投影只保留审核必要字段。
- 不维护两套规则库。
- 不设置分类数量配额和规则数量下限。
- 重要来源文件可以产生较多规则，不重要文件可以产生零条规则。
- 规则不再由来源文件顺序决定。
- 给模型的 Schema 为轻量 DTO，不直接注入完整领域模型 Schema。
- 规则抽取使用当前 RuleSet + 当前批次生成 delta 操作。
- `normal + evidence_check/cross_check` 由代码确定性提升为 `important`。
- 不合理组合先标准化，不因为单个字段错误丢弃有效规则。
- add/merge 时完整 RuleSet 正确保存当前规则来源，来源元数据不进入 LLM 投影。
- merge 同时合并 `priority/verification/evidence_types`。
- 超过30条时触发容量合并，不能按文件顺序直接拒绝当前 add。
- 串行增量结束后不再调用 LLM 做全局整理。
- 最终只校验 ID 唯一、字段完整、组合合法、稳定排序和总量上限。
- 招标原文回查统一通过向量召回 + rerank。
- 投标摘要输出结构化事实，而不是泛化摘要。
- 投标摘要模型只输出 `match_status/match_reason/summary`。
- 资料分类不理解 RuleSet，只输出资料类型、状态、原因和两种用途摘要。
- 资料分类以原始文件为单位，每个文件只调用一次 LLM。
- 主 Agent 资料目录按 `evidence_type` 分组并保留文件级列表，不做二次摘要聚合。
- `manual_review` 资料不启动资料子 Agent。
- 资料核验工具要求主 Agent 提供 `rule_id/verification_request/evidence_type`。
- `rule_id` 只进入工具引用记录，不进入资料子 Agent HumanMessage。
- 资料子 Agent 由工具层按 `bidder_id + evidence_type` 限制资料范围。
- 资料子 Agent 初始只看到该类型文件的 `file_id/evidence_summary` 列表。
- 资料原文片段只通过子 Agent 的检索工具调用返回。
- 资料子 Agent 输出为 `status/summary/evidence_chunk_ids`。
- 投标检索、招标检索和资料检索统一使用实际 chunk ID。
- 一条规则可以关联多个资料核验结果。
- 所有 LLM 调用均使用独立的 SystemMessage 与 HumanMessage Markdown 模板。
- 稳定指令与本次运行数据在 Trace 中明确分离。
- 主 Agent 输入使用 Markdown 主结构和精简 JSON 数据。
- 主 Agent 初始输入不默认携带投标文件预检索片段。
- 不新增独立 `app/audit/retrieval_context.py`。
- 各 BaseTool 内部完成业务过滤、多 query 合并、按 `chunk_id` 去重和结果预算。
- ToolMessage 统一返回 `chunks`，每个片段包含实际 `chunk_id`。
- 主 Agent 允许信息充分时直接结束，也允许按需调用三类工具。
- 主 Agent 最终输出为文件总体总结、分类总结和规则级简短结论。
- 规则级结论使用 `summary.reason` 和三类可选 chunk ID。
- 最终 Finding 使用相同的三类 chunk ID，报告生成时再读取真实来源信息。
- 没有工具引用时三个 chunk ID字段为空，不伪造来源。
- `not_matched/uncertain` 文件也进入 JSON 和 Word。
- 图片资料不接 OCR，统一进入明确的人工核验路径。
- DeepSeek-V4-Flash 长上下文环境下能够完成真实比赛数据审核。
