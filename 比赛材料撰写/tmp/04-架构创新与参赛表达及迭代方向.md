# 架构创新、参赛表达与后续迭代方向

整理日期：2026 年 10 月 3 日。

本文整理近期讨论，供后续修改参赛材料、准备答辩和判断研发方向使用。用户提供的实践背景、当前实现、分析判断与未来设想分别标明；本文件不是已经确定的开发计划，也不将待验证收益写成既有成果。

市场事实与竞品来源见 [01-市场与竞争调研](01-2026市场与竞争调研.md)和[02-来源索引](02-一手来源与证据索引.md)，具体对照方法见 [03-材料调整与验证方案](03-参赛材料调整建议与验证方案.md)。本文重点补充架构设计为什么有意义，以及如何在有限篇幅中表达。

## 一、讨论背景与需要保留的判断

### 1. 项目起点与当前定位

据用户介绍，项目最初用于电力交流会的招标赛道。当时有队伍采用通用 Agent 框架搭配 Skill 的方案，最终表现不如本项目。早期任务文档也保留了电力智能招标审核的设计背景。

这是一项有价值的实践经历，可以作为追查设计贡献的起点。目前记录来自用户陈述，尚未整理活动正式名称、评价口径、参赛配置和结果材料，因此不能自动改写为已获某奖项，也不能单独归因于多智能体架构。

当前产品定位是跨行业、面向多场景的招投标材料审核，电力采购作为首批验证样本。“垂直”主要指围绕招投标审核任务进行专门设计，不意味着只适用于电力行业；“全场景”表达通用架构方向，不表示所有行业或交易环节都已验收。

### 2. 用户提出的核心问题

- 2026 年通用模型和 Agent 的能力已经提高，专门设计的系统可能在短时间内被更通用、更便宜的方案替代。
- 架构值得深入讨论的内容包括工具接口、提示词组织、分批与压缩、主子 Agent 的分工，不能仅以“大家都用了 Agent”判断同质化。
- 线上材料篇幅有限，评委很难深入理解实现细节；线下答辩更适合展开技术取舍。
- 将现有 config 配置扩展成 Web 配置平台，是可考虑的产品化方向；单纯增加配置界面，不直接提高审核效果。

据此形成的分析建议是：分别评价业务能力、架构贡献、材料表达和产品化便利性。它们相互关联，但需要各自的证据。

## 二、当前架构可以论证的三项设计贡献

以下是应用型架构创新的候选主线。它们有实现依据，但尚不能据此声称学术首创、行业唯一或性能领先。

### 1. 项目规则、资料事实与本次判断分开维护

项目规则回答本次应满足什么要求；投标方资料保存材料自身的事实及关联；审核任务结合本次条件形成判断。资料入库阶段不提前把某一项目下的合规结论固化到材料中。

这种分离有助于表达三个不同的生命周期：项目要求可以变化，已有资料可以在授权范围内复用，本次判断仍需重新作出。值得验证的是它能否减少跨项目条件混用、重复资料整理及人工维护工作。

实现依据：[资料归属模型](../../app/models/documents.py)、[Task23 的职责与边界](../../tasks/23-投标方资料入库Agent与资料库维护.md)。现有资料库的独立归属不等于已经具备完整的持续追加、替换和维护能力，不能扩大现有产品承诺。

### 2. 以具体核验事项组织跨材料协作

主审核 Agent 围绕规则提出具体核验问题，说明主体、对象、编号或参数、判断标准以及起始文件。一个规则可以包含多个事项，一个事项可以联合多份材料。

简洁摘要帮助选择文件，详细摘要提供核验线索，原文与图片用于进一步查证，直接关系帮助连接相关材料。架构贡献的讨论重点是如何形成有边界、可回答的核验问题，以及怎样把相关证据交给负责判断的环节。

值得验证的收益是跨材料问题的发现与判断质量；同时需要检查摘要遗漏、选材错误和额外调用成本。主会话变短不等于全系统更便宜。

实现依据：[事项核验接口](../../app/tools/bid_tools.py)、[摘要与关联视图](../../app/audit/context.py)。当前关联扩展为一层直接关系，不应包装成完整知识图谱推理。

### 3. 模型判断与程序性约束分开承担

模型负责解释条款、选择查询、形成判断；程序负责冻结依据、限制资料范围、登记实际读取来源，并检查报告结构及已抽取规则的覆盖情况。正式输出依据统一结果生成，避免不同输出形式各自重新判断。

这种设计将部分业务要求落实到可执行的约束中。模型可以在工具范围内选择核验路径，但来源和交付格式需要接受程序检查。

需要准确表述其能力边界：

- 来源已读取、角色正确，不代表该来源足以支持结论。
- 已抽取规则全部有结果，不代表招标文件中的要求全部抽取完整。
- 报告格式通过，不代表每项业务判断正确。

实现依据：[审核依据冻结](../../app/services/audit_management_service.py)、[来源台账](../../app/audit/sources.py)、[报告解析校验](../../app/reports/report_parser_v2.py)。适合称为程序性约束和产物检查，不宜直接称为程序验收审核质量。

三项贡献可合并为以下表述：

> 面向招投标材料审核，将项目规则、可复用资料事实与当前任务判断分离，以具体核验事项组织跨材料协作，并通过冻结依据、实际读取记录和报告校验约束交付过程。

## 三、内部技术细节如何支撑这条主线

| 设计内容 | 可以深入讨论的理由 | 不能直接推出的结论 |
| --- | --- | --- |
| 工具接口 | 将业务核验问题落实为明确输入、访问范围和执行反馈，使模型得到可操作的能力 | 工具越多，审核就越准确 |
| 提示词组织 | 明确当前职责、规则解释、资料用途、结论边界与反馈处理，减少不同阶段目标混杂 | 提示词更长或更复杂就更专业 |
| 分批阅读 | 在输入预算内保持文档结构和阅读进度，使长材料能够继续处理 | 分过批就没有遗漏，或一定优于直接读全文 |
| 上下文压缩 | 保存必要进度、已知信息和未完成事项，为后续调用腾出空间 | 压缩不会损失线索，或适用于所有模型 |
| 主子 Agent | 在统筹审核与具体取证之间分配职责和上下文，允许围绕事项深入读取 | 多 Agent 天然优于强单 Agent |
| 双摘要与直接关系 | 分别支持选材、核验及跨文件联查，控制每次进入上下文的信息 | 摘要可以替代原文，或一层关系足以覆盖所有关联 |
| 增量草稿和程序检查 | 保存阶段成果，发现结构缺项或非法引用并反馈修正 | 有草稿就一定能完成，或完整报告就一定正确 |

任务历史能帮助解释设计动机。例如 [Task15](../../tasks/15-规则分级与批量智能审核重构.md)因调用膨胀调整工作单元，[Task21](../../tasks/21-规则抽取Agent与增量规则库维护.md)撤销规则条数硬上限及机械压缩。它们表明方案在随实际问题演进。历史记录可以支撑“为什么这样设计”，性能收益仍需同条件对照。

## 四、模型升级后，哪些设计可能变化

| 设计依据 | 当前例子 | 对演进的分析 |
| --- | --- | --- |
| 适应当前模型的能力与成本 | 主子分工、双摘要、分批、压缩、轮数和收尾策略 | 模型变强后可能简化、合并或被替换；过多约束也可能限制新模型发挥 |
| 表达业务对象和交付要求 | 规则与资料归属、本次版本、可访问范围、来源记录和结果结构 | 业务要求通常更稳定，但实现方式仍可能被通用平台吸收 |

Anthropic 在 2026 年 4 月的工程文章中报告：为旧模型设计的上下文重置措施，在更强模型上失去必要性；其设计因此强调实现可变、接口相对稳定。这支持“应持续重新评估执行策略”的判断，不证明本项目哪项机制已经可以删除。[官方文章](https://www.anthropic.com/engineering/managed-agents)

通用 Agent 搭配 Skill 可以调用专用检索、冻结、核验和报告服务。两种路线可以接近，不能根据是否自行实现框架就判断高下。业务要求稳定也不等于形成不可复制的壁垒。

建议保留的演进原则是：让模型、角色数量、摘要与检索策略能够随效果变化；尽量使调整推理方式时，业务对象、依据记录和结果接口仍可继续使用。这是设计方向，不表示当前代码已实现任意执行引擎的无缝替换。

比赛中的设计贡献与长期商业壁垒需要分别论证。一项机制在当前任务上有效，即有可讨论的工程价值；未来可替换，不抹掉已有贡献，也不支持预先宣称长期领先。

## 五、线上参赛材料如何表达

### 1. 采用“业务困难—关键机制—可观察结果”组织创新点

线上阅读条件下，正文需要让评委迅速理解设计与业务结果之间的关系。细节可以压缩，但不能只剩“高效、精准、可追溯”等形容词。

| 业务困难 | 正文呈现的关键机制 | 需要补充的证据 |
| --- | --- | --- |
| 要求散落在正文、附件及澄清中，容易遗漏或混用 | 整理项目规则，保留来源、适用条件与修订关系 | 要求覆盖和条件保留情况【待实测】 |
| 一项资格或业绩需要多份材料共同证明 | 以具体事项组织联合核验，回查原文和图片 | 跨材料问题发现、误报与证据支持情况【待实测】 |
| 长材料审核可能漏项或中途无法交付 | 分批推进、保存阶段成果、检查正式报告 | 完整产出、漏项、耗时和成本【待实测】 |

“可能改善什么”与“已经改善多少”在行文上保持区别。线上材料保留关键机制和因果解释；工具字段、提示词片段、压缩触发条件及失败分析适合放在技术备查材料和答辩准备中。

### 2. 用一个贯穿案例解释架构

以下为写作示例，尚未对应已验收样本，不能直接标为真实运行结果。

某项业绩要求同时限定业务对象、完成时间及验收状态。投标文件声称满足，合同记载了承接情况，验收文件还需核对主体、对象和日期。系统依次展示：

1. 招标要求整理成什么审核条件，原始依据在哪里。
2. 投标文件作出了什么响应，哪些部分需要证明。
3. 选择了哪些合同及验收材料，为何需要联合核验。
4. 原文支持了什么、存在什么矛盾或仍缺少什么。
5. 最终给出何种判断，复核人员怎样回到依据。

一个这样的案例能够承载规则组织、事项委派和来源追查。正式材料应换成可披露的实际样本，填入人工基准、真实输出和对照结果，不只展示最漂亮的一次成功过程。

### 3. 三份附件各有侧重

| 附件 | 应承担的表达任务 |
| --- | --- |
| 项目简表 | 一句话说清对象和价值，浓缩关键机制，列少量有清楚口径的指标 |
| 项目说明书 | 展开业务困难与三项架构贡献，用核心技术图、贯穿案例及对照结果支撑 |
| 商业计划书 | 说明使用者、购买理由、交付范围和维护方式，区分功能便利与可量化收益 |

后续修改仍需遵守原模板字数上限，优先替换泛化表述，减少同一能力在不同段落反复出现。本文不作为第四份正式参赛附件。

## 六、配置平台的价值与边界

用户提出的方向是：将现有 config 配置通过 Web 管理，减少后端文件操作。项目本身已有配置文件和模型适配，后续应表述为配置的可视化管理与产品化，不应将现状概括为所有参数都写死在代码中。

这一方向的直接价值包括降低操作门槛、便于部署调整，以及管理不同模型或执行方案。它主要属于使用和维护能力；仅将参数搬到网页，不能推出漏检减少、误报下降或运行更快。

如果进一步具备以下能力，配置管理可以支持审核效果迭代：

- 记录配置、提示词和模型版本，使一次运行可以追查。
- 在固定样本上比较调整前后的质量、完整产出和成本。
- 保存人工复核结果及错误原因，识别新版本修复和引入的问题。
- 对验证无收益或导致退化的配置保留撤回依据。

这些均为后续设想，未纳入已实现清单。提升效果需要有效的业务调整和验证，配置界面承担操作与记录作用。具体哪些配置开放给什么角色，也需要结合使用场景决定，不必一次暴露所有底层参数。

## 七、后续迭代分别看效果、产品化与验证能力

以下为候选方向及判断依据，不预设开发顺序、验收指标或实施承诺。

### 1. 直接影响审核效果的候选方向

| 问题 | 可以研究的改进 | 观察是否有效 |
| --- | --- | --- |
| 要求遗漏或条件失真 | 更完整地处理阈值、时间、单位、适用主体、例外和澄清关系 | 原始要求遗漏、条件误用及人工修订是否减少 |
| 证据相关但支持不足 | 检查多份材料是否共同对应同一主体、对象、事项及时间，并区分支持、矛盾和不足 | 无依据判断和跨材料误判是否减少 |
| 明确数值条件核算不稳 | 研究模型提取日期、金额、数量、单位，程序比较，模型结合上下文解释 | 在可形式化事项中，核算错误是否减少，是否引入抽取或适用错误 |
| 长材料未完成或报告缺项 | 根据失败原因调整阅读、调用预算、保存和修复策略 | 在同一预算口径下，完整产出及总成本是否改善 |

程序比较为候选接入方向，不能因仓库中存在比较函数就写成当前审核已使用确定性计算引擎。程序也需正确输入和适用条件，不能把语义理解问题一并宣称解决。

### 2. 产品化方向

Web 配置、导入便利、任务管理、报告使用体验和部署维护，可以提高可用性及交付效率。它们有独立价值，适合用操作时间、配置错误、接入工作量等指标评价，不必都包装为审核准确率创新。

### 3. 支持持续改进的方向

固定样本、错误分类、运行版本和人工复核记录，帮助判断改动是否有效。这类能力让后续优化有依据，本身不直接保证业务质量。

对主子分工、双摘要、分批和压缩的调整，建议保留强通用 Agent、共享本项目工具的单 Agent、当前完整流程三组参照。详细实验设计沿用 [03-验证方案](03-参赛材料调整建议与验证方案.md)，避免通过弱单轮基线证明优势。

## 八、用于后续工作的表达口径

- **目前可以陈述：** 已围绕招投标审核形成具体业务建模、事项核验、依据管理和报告交付机制；项目具有来自实际赛道的实践背景。
- **需要验证后升级为优势：** 这些机制带来的质量、成本、速度、复核投入及跨行业适配收益。
- **属于后续设想：** Web 配置平台、配置与评测联动、更深入的程序比较，以及随模型能力调整执行结构。
- **保持开放：** 最终需要几个 Agent，哪些摘要与约束继续保留，何种首发任务最有价值，均由任务表现与使用反馈判断。

后续参赛写作以业务难题组织创新点，以内部设计解释实现机制，以案例和指标支撑价值；配置管理放在产品化与持续迭代中说明。这样既保留技术设计的实质，也适应线上材料的阅读条件。
